4 · Deposit details & confirmation

Bags and valuables are simple counters — no free text. The physical token number is the one thing a volunteer must key in from the basket; the system rejects a token that's already marked occupied, catching mixed-up baskets before they become a lost-item problem.

  • On success: a confirmation screen shows the masked phone, the token/hook number, and “place belongings on hook #501”.
  • One token = one active transaction. Adding more items later goes through Add More Items, not a second deposit.

5 · Collect / Manage Deposit

One workspace per token instead of scattered actions. A volunteer finds the token, then picks exactly one of four things to do — the system derives partial vs. full status from remaining quantity, so nobody has to remember which button means what.

  • Collect Partially keeps the same token active for whatever's left.
  • Collect All immediately frees the hook and closes the transaction.
  • The phone shown for verification is masked — the volunteer only needs the customer to confirm the last digits.

Resilience

Ashram wifi drops. The counter can't.

Every write — deposits, collections, resident registration, and now admin settings changes — goes through the same offline queue. Nothing is lost to a dead connection; nothing silently fails.

●

Queued locally

Offline actions save to the phone instantly with a clear “will sync automatically” toast, and stay visible in a pending-items list.

↻

Auto-sync

Reconnects retry every few seconds in the background; a manual “Sync Now” is always available too.

⚑

Admin changes included

An admin editing settings or the resident directory offline used to fail silently. It now queues like everything else — other volunteers' phones simply see the updated settings the next time they load that screen after it syncs.

And if the digital system itself is ever fully down: the ashram's existing manual token-and-paper process is still there underneath it, unchanged, as the ultimate fallback.

Privacy & security

Four identity stores, one masking rule, one narrow purge

Every phone number the app ever shows a volunteer is masked to the last 4 digits — across all four places one can live. What differs between them is how long each is kept, and that difference is deliberate.

V

Volunteer Directory

Staff who can log in. Admin-managed, phone masked in the list. Kept indefinitely — removed only when an admin removes that volunteer.

R

Resident Directory

ID → name + masked phone, built the first time a resident registers. A deliberate, permanent membership record — that's what makes every later scan instant. Exempt from the purge below; removed only if an admin removes that ID.

T

Transactions

One record per deposit: token, bags, valuables, phone, name, timestamps. This is the only store the automatic purge touches — phone and name are redacted once a completed transaction is older than the retention window.

↻

Visitor recognition

Not a stored directory — a live check of “has this phone deposited before?” against Transactions. A visitor who returns within the retention window gets their name pre-filled; once their last visit ages past retention and purges, so does the recognition. Convenience that expires with the data, by construction.

Why the purge stays this narrow

The purge only ever redacts phone and name on completed transactions — nothing else on that record, and neither Directory. A purged transaction can still show a Resident ID next to it; that's not a leak — the Resident Directory already keeps that exact ID→name/phone match permanently, by design (that permanence is what makes repeat scans instant). Widening the purge to also strip Resident IDs from old transactions wouldn't remove any information a lookup couldn't already recover; it would just make History harder to search.

Under the hood

Deliberately small surface area

One server file, one HTML file, one JSON datastore — chosen so the whole thing installs and runs anywhere with just Node.

FE

Frontend

HTML5, CSS3 (mobile-first grid/flexbox), vanilla JavaScript (ES6+), Fetch API, Web Storage API (localStorage) — no build step.

BE

Backend & data

Node.js + Express, deployed on Render's free tier. A single JSON file datastore via the fs module — zero native database dependencies.

📷

Scanning & sync

qr-scanner for camera-based QR capture, chosen specifically for its reliability on iOS Safari; phone + OTP auth (demo-simulated); a localStorage-backed offline queue with automatic background sync.

Path to production

What this needs before it holds anyone's real belongings

This is a working prototype, proving the product idea — not yet load-tested for a real deployment. Here's what would actually need to change to run it for real: 500+ hooks, 10–15 volunteers transacting at once, and up to 3 admins occasionally updating settings.

01

Concurrent writes at volume

Every request currently reads and rewrites the whole data.json file. That's safe today only because each route finishes its read-modify-write in one uninterrupted pass — it won't hold up under 10–15 volunteers transacting at once over months of history. Needs a real datastore (SQLite with WAL, or Postgres).

02

Real authentication

Admin- and volunteer-gated actions currently trust whatever phone number the client sends, checked only against the server's volunteer list — there's no session token tied to a verified OTP. Needs signed, expiring sessions issued at OTP verification, and a real SMS gateway with rate-limiting.

03

Durable hosting

Render's free tier resets its disk on every restart or redeploy — fine for a prototype, not for real transaction data. Needs persistent storage (or a managed database) plus basic uptime monitoring.

04

500+ is a setting, not a wall

Raising totalHooks to 500+ is a one-line config change — the app doesn't otherwise care how many hooks exist. The real scaling question is Card 01. Admin changes from up to 3 admins need no extra work: they're already infrequent and don't conflict in practice.
